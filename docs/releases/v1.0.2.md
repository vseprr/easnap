# Easnap v1.0.2

A maintenance release: no new features. It fixes wrong colours in trimmed MP4
files on some machines and makes Blur, Pixelate and Spotlight respond faster
while they are being drawn.

## Fixed

- **MP4 trimming**
  - A trimmed MP4 could come out with wrong colours when the recording's
    height was not a multiple of 16, for example a region 120 pixels high.
    The video decoder pads such pictures, and the exporter passed the padded
    frame on as if it were the picture. This happened on machines whose H.264
    encoder does not read Direct3D surfaces itself, typically those without a
    hardware encoder. Machines with a hardware encoder that reads them were
    not affected.
  - The recording itself was never damaged. If a trim made with v1.0.1 or
    earlier looks wrong, open the original recording and export it again.

## Performance

- **Screenshot editor:** drawing, moving or resizing a Blur, Pixelate or
  Spotlight effect recomputes only the part of the image the edit can change,
  instead of rebuilding the whole screenshot on every pointer move. Changing
  the Spotlight dim level, and adding the first or removing the last
  Spotlight, still recompute the whole image because they change every pixel.

```powershell
Get-FileHash .\Easnap-v1.0.2-windows-x64-setup.exe -Algorithm SHA256
```

and temporary recordings stay in `%LOCALAPPDATA%\Easnap` and are not removed
by the uninstaller.

## Validation

Tested on one development PC: Windows 10, two 1920x1080 displays at 125 %,
NVIDIA hardware decoder and encoder.

- The Release x64 build succeeded with warnings as errors. Both executables
  report 1.0.2.0.
- The Full tier passed on those binaries in a single run: 34 of 34 tests, none
  retried, with the visible-desktop tests on the secondary display. The six
  long-repeat (soak) tests were not run for this release.
- The trim test now decodes the trimmed file and compares its picture with the
  source. On this PC's hardware path the mean channel error is 1.11. With
  Direct3D disabled by a temporary local switch it was 37.89 before the fix
  and 1.11 after. The hosted build machine, which has a software adapter and a
  software encoder, failed the same comparison before the fix and passes now.
- The editor test compares the incrementally updated image with a full
  rebuild after each of 720 random edits and checks that nothing outside the
  reported area changed.
- An installer built from the tested binaries was installed silently, the
  installed application started and reported 1.0.2.0, and it was uninstalled
  cleanly, on that same PC only.
- The trim fix for encoders that lock a hardware surface was exercised only on
  the hosted machine's software adapter, not on a physical GPU with a software
  encoder. The editor's speed on a 4K screenshot was not measured.
- No scale factor other than 125 %, no mixed-DPI layout and no other Windows
  version, GPU or audio device was used.

Details, including unsuccessful runs, are in
[project status](https://github.com/vseprr/easnap/blob/v1.0.2/docs/project-status.md).

## Known issues and limits

- **Trim resizing:** transient redraw artifacts can still occur while resizing
  or maximizing the Trim window. This is unchanged from v1.0.0.
- **Blur, Pixelate and Spotlight while dragging:** only the changed part is
  recomputed, but the editor still repaints the whole image for a Spotlight
  preview and while any annotation is moved, which can lag on a 4K screenshot.
- **Compatibility coverage:** physical testing covers two 1920x1080 displays
  at 125 %. Layout at other sizes and scale factors is covered by automated
  layout tests only. Other GPUs, audio devices, mixed-DPI layouts, HDR displays
  and accessibility tools have not been checked on real hardware.
- **Very large recording regions:** a region beyond the H.264 encoder's limits
  (for example across two 4K displays) fails to start with a general message.
- **GIF preview:** the preview plays the source recording. GIF palette and
  frame-rate conversion happen during export.
- **MP4 trimming:** cut points follow video/audio sample granularity. Late
  excerpts from long recordings can take longer because decoding starts at the
  source beginning.
